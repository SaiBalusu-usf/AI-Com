**Strategy under these constraints** (no silent scraping, no fabricated data or
metrics, per §2 and §4):

1. Build the **entire codebase** — data pipeline, eval harness, baselines,
   fine-tuning, ablation configs, tables/figures — fully config-driven and
   tested.
2. The committed 200-row fixture (`data/fixtures/mini.jsonl`) is generated by a
   **seeded synthetic match simulator that emits exact Cricsheet-format JSON**
   plus clearly-labelled synthetic reference commentary
   (`reference_source: "synthetic_v1"` on every row). It exists so every gate,
   test, and `make mini` runs end-to-end. It is a *pipeline* fixture, not
   research data, and the DATASET_CARD says so loudly.
3. Every network-dependent step (real Cricsheet download, Kaggle commentary,
   model weights, torch install) is implemented, documented, and **verified as
   far as the environment allows**, with the exact command for the student's
   machine recorded in README and EXPERIMENTS.md.
4. Metrics that need blocked models (BERTScore, model-arousal half of the
   excitement scorer) are never stubbed: when unavailable they are recorded in
   `metrics.json` as `{"status": "unavailable", "reason": ...}` and the run
   log says why (§2 rule 7 — fail loudly).

## Risks / conflicts noticed in the build prompt

1. **R1 (resolved above):** §8 Phase 1 gate says "real 200-row fixture"; the
   egress policy makes that impossible in-session. Mitigation: synthetic
   fixture in exact Cricsheet schema + `scripts/download_data.py` that
   rebuilds the fixture from real data with one command when network allows.
2. **R2:** B2 "local 7–8B instruct model" is not runnable on 4 CPU cores at
   <1 s/ball regardless of network; config defaults to Qwen2.5-1.5B-Instruct
   (few-shot) with the 7B config provided for CUDA machines.
3. **R3:** RQ3's "<1 s per ball" latency target is defined on HARDWARE; on a
   CPU-only container this is only meaningful for the template baseline.
   Latency is still measured identically for every system.
4. **R4:** The excitement scorer's model-arousal half needs a blocked HF
   model. v1 therefore ships a heuristics-only mode (config-selected, weights
   renormalized) and the mandatory human-reference validation runs against
   whichever mode is active; both modes are implemented.
5. **R5:** §5.3 BERTScore `rescale_with_baseline=True` requires downloading
   baseline files from HF — recorded as unavailable in-session (see above).
